# Memory Rollup — Month / Year Span Design

**Status:** Draft
**Date:** 2026-04-26
**Spec parent:** `docs/superpowers/specs/2026-04-24-memory-digest-design.md` (rollup pipeline)

## Problem

The Memory timeline supports four spans: Day, Week, Month, Year. Day
and Week show a synthesized rollup banner ("DAY ROLLUP" / "WEEK
ROLLUP") below the span cards — title plus key bullet points,
generated by the Anthropic LLM and cached server-side per period.
Month and Year spans show no banner. Users get no synthesized digest
for longer windows even though those are the spans where a synthesis
matters most (a year's worth of events is impossible to scan card by
card).

## Goals

- Surface a synthesized rollup for Month and Year spans, visually
  identical to the existing Week/Day banner.
- Generate Month rollups from raw item summaries in the calendar month
  (same pipeline as Week, wider window).
- Generate Year rollups from the twelve constituent monthly rollups
  (rollup-of-rollups) — cheaper, more structured, scales past 1k+
  items per year.
- Same caching primitives as Day/Week (`summarizer_store` keyed by
  `target_kind` + `target_id` + `lang`).
- Same user controls: auto-fetch on span change, manual `Regenerate`
  button.

## Non-Goals

- Showing Month/Year rollups on the Home brief. Out of scope — Home
  surfaces Day/Week only and that's the right ambient cadence.
- Cascading regeneration — `Regenerate` on Year does **not** rebuild
  the underlying monthly rollups. The user can re-run individual
  months from the Month banner if needed.
- Refactoring `screens-a.jsx`. The file is large but the additions
  are pattern-symmetric with existing rollup state/UI; restructure
  is out of scope.
- Composing Month from Week rollups. Week and calendar-month
  boundaries don't align (a week can straddle two months) and
  attributing a straddling week to one month vs the other adds
  complexity for negligible gain.

## § 1. Architecture & Data Flow

```
┌──────────────────────────────────────────────────────────────┐
│ Memory screen (screens-a.jsx)                                │
│                                                              │
│   timelineSpan = 'month' ──► useEffect                       │
│       monthStartMs = first day of cursor's month @ 00:00     │
│       runRuntimeActionA('memory.rollup.month.get', { … })    │
│                                                              │
│   timelineSpan = 'year'  ──► useEffect                       │
│       yearStartMs  = Jan 1 of cursor's year   @ 00:00        │
│       runRuntimeActionA('memory.rollup.year.get',  { … })    │
└──────────────────────────────────────────────────────────────┘
                            │
                action-registry.js
                            │
                  shogun-api.js (call)
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
shogun_memory_month_rollup_get    shogun_memory_year_rollup_get
            │                               │
            ▼                               ▼
summarize_month_rollup           summarize_year_rollup
   (items in [start, end))            (12 monthly rollups)
            │                               │
            ▼                               ▼
   summarize_rollup                  for each month:
   (existing pipeline)                 cached month_rollup
            │                          else summarize_month_rollup
            │                               │
            └──────────────┬────────────────┘
                           ▼
              summarizer_store::upsert
              (target_kind, target_id, lang)
```

Period boundaries are calendar-aligned in **local time** for
intuitive UX (the user's "April" is their local April, not UTC's).
The UI computes the period start in local ms and the Rust side
derives the end via chrono date arithmetic.

## § 2. Data Model & Cache Keys

Two new `target_kind` values, parallel to existing `week_rollup` /
`day_rollup`:

| target_kind     | target_id format | example     |
|-----------------|------------------|-------------|
| `month_rollup`  | `YYYY-MM`        | `2026-04`   |
| `year_rollup`   | `YYYY`           | `2026`      |

Cache lookup unchanged: `summarizer_store::get_cached(target_kind, target_id, lang)`.

## § 3. Backend (Rust)

### 3.1 `summarizer.rs`

**`RollupKind`** enum extended:

```rust
pub enum RollupKind { Week, Day, Month, Year }
```

All match arms updated:

| arm                 | Month                                              | Year                                                        |
|---------------------|----------------------------------------------------|-------------------------------------------------------------|
| `target_kind`       | `"month_rollup"`                                   | `"year_rollup"`                                             |
| `window_label`      | `"Month"`                                          | `"Year"`                                                    |
| `items_intro`       | `"Items this month (sorted by priority):"`         | `"Monthly rollups this year (chronological):"`              |
| `fallback_title`    | `Month of YYYY-MM` / `今月（YYYY-MM）`             | `Year of YYYY` / `今年（YYYY年）`                           |
| empty title         | `Quiet month` / `静かな月`                         | `Quiet year` / `静かな年`                                   |
| empty key_point     | `No activity this month.` / `今月のアクティビティなし` | `No activity this year.` / `今年のアクティビティなし`       |
| context cap         | 60 items                                           | 12 monthly rollups (no cap needed — fixed cardinality)     |

**Period helpers** (new):

```rust
pub fn format_month_id(month_start_ms: i64) -> String;  // "YYYY-MM"
pub fn format_year_id(year_start_ms: i64) -> String;    // "YYYY"
fn month_window(month_start_ms: i64) -> (i64, i64);     // (start, next-month-start)
fn year_window(year_start_ms: i64)   -> (i64, i64);     // (start, next-year-start)
```

`month_window` / `year_window` use chrono `NaiveDate::checked_add_months` /
`with_year` so the end ms reflects calendar-aware advancement (handles
month length variation, leap years).

**`summarize_month_rollup`** (new): identical shape to
`summarize_week_rollup` — derives end via `month_window`, delegates
to existing `summarize_rollup(start, end, RollupKind::Month, lang)`.

**`summarize_year_rollup`** (new, **does not delegate to `summarize_rollup`**):

```rust
pub async fn summarize_year_rollup(year_start_ms: i64, lang: &str) -> Result<Summary, String> {
    let (year_start, year_end) = year_window(year_start_ms);
    let id = format_year_id(year_start);

    // Gather (or generate) the 12 monthly rollups inside [year_start, year_end).
    let monthly: Vec<Summary> = collect_monthly_rollups_for_year(year_start, year_end, lang).await?;

    if monthly.iter().all(is_empty_rollup) {
        return Ok(empty_year_summary(&id, lang));
    }

    let user_content = render_year_context(&monthly, &id);
    let system = rollup_system_prompt_for_lang(lang, RollupKind::Year);
    let tool   = emit_memory_summary_tool();

    match crate::llm::anthropic_tool_complete(&system, &user_content, &tool, SUMMARIZER_MODEL).await {
        Ok(input) => build_rollup_from_tool_input(&id, RollupKind::Year, &input, lang)
                       .or_else(|_| Ok(year_heuristic_fallback(&id, &monthly, lang))),
        Err(_)    => Ok(year_heuristic_fallback(&id, &monthly, lang)),
    }
}
```

`collect_monthly_rollups_for_year` walks each month-start within the
year, looks up cached `month_rollup`, and on miss calls
`summarize_month_rollup` then `summarizer_store::upsert`. Future months
(month_start > now) are skipped.

`is_empty_rollup(s: &Summary) -> bool` parses `s.raw_json` and returns
`true` when it contains `{"rollup":"empty"}`. The empty-state path in
`summarize_rollup` already writes that marker; we reuse it instead of
sniffing `model == "heuristic"` (which also fires on LLM-failure
fallbacks that *do* have content).

`render_year_context` formats each monthly rollup with its month label:

```
Year: 2026

Monthly rollups (chronological):

[Jan 2026] {month.title}
  · {keypoint1}
  · {keypoint2}

[Feb 2026] {month.title}
  · …
```

**Fetch effects (after the day-rollup effect at line ~2085):**

```js
// Month rollup
useEffect(() => {
  if (!summaryEnabled || timelineSpan !== 'month') { setMonthRollup(null); return; }
  const cursor = new Date(timelineCursor);
  const monthStart = new Date(cursor.getFullYear(), cursor.getMonth(), 1, 0, 0, 0, 0);
  const monthStartMs = monthStart.getTime();
  let cancelled = false;
  setMonthRollupLoading(true);
  (async () => {
    try {
      const lang = (typeof document !== 'undefined' && document.body && document.body.getAttribute('data-lang')) || 'en';
      const res = await runRuntimeActionA('memory.rollup.month.get', { monthStartMs, lang }, { silentError: true });
      if (cancelled) return;
      setMonthRollup(res?.ok && res.data?.rollup ? res.data.rollup : null);
    } finally {
      if (!cancelled) setMonthRollupLoading(false);
    }
  })();
  return () => { cancelled = true; };
}, [timelineSpan, timelineCursor, summaryEnabled, batchSummarizing]);

// Year rollup — same shape, uses Jan 1 of cursor year
```

## § 5. Error Handling & Empty States

- **Empty window** (zero indexed items in the period): `"Quiet
  month"` / `"Quiet year"` heuristic Summary, same shape as the
  existing Day/Week empty-window paths.
- **LLM error** (network / rate limit / parse): `month_heuristic_fallback`
  and `year_heuristic_fallback` produce a deterministic Summary from
  the input items / monthly rollups. The banner still renders.
- **Year with all-empty months**: short-circuit before LLM call;
  return the empty-year heuristic.

## § 6. Testing & Verification

Manual:

1. `npm run check:rust` — no errors / new warnings on the new
   commands and enum arms.
2. `npm run check:ipc-mock` — IPC mock stays in sync with the two
   new actions.
3. `npm run check:actions` — action registry is consistent.
4. `npm run dev:desktop` → Memory screen:
   - Switch span to Month: banner appears, regenerate works.
   - Switch span to Year: banner appears; first run triggers up to
     12 month rollups (visible in app log); cached run is fast.
   - Switch span back to Day/Week: existing banners still render.
5. With `summaryEnabled=false`: no banners at any span (existing guard
   carries through).

Automated (out of scope for this spec, follow-up):
- Unit tests for `format_month_id` / `format_year_id` (calendar math
  edge cases — Dec→Jan crossover, leap-year Feb).
- Unit test for `collect_monthly_rollups_for_year` skipping future
  months.
